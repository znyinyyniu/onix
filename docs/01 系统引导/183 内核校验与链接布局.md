# 内核校验与链接布局

`make qemu-usb-xhci` 使用 `-vga std` 和 `-serial stdio`。串口日志出现在执行 make 的终端里，QEMU 窗口只显示帧缓冲。

内核变大并链入 `usb_storage.o` 之后，终端停在 GRUB 的警告上，窗口是黑的：

```text
WARNING: no console will be available to OS
```

这句出现两次，是因为 `src/utils/grub-uefi.cfg` 里写了 `terminal_output serial console`，两个输出端都接到了同一条串口。

## 日志并没有被 usb_storage_init 吃掉

`xHCI init done` 在 `xhci_init()` 返回之前用 `LOGK` 打出，`usb_storage_init()` 是下一条语句。`LOGK` 走串口，`serial_write()` 直接 `outb` 写 UART。只要执行到这一行，终端里一定能看到。

用 `-vga none` 启动时，串口顺序是：

```text
xHCI init done, 1 device(s)
USB storage init...
USB disk capacity 524288 sectors
USB storage init done, 1 disk(s)
Mount root file system...
```

`-vga std` 时连 `Serial 0x3f8 init...` 都没有。停住发生在 `serial_init()` 之前，不是 U 盘初始化把这行日志冲掉了。

## 停在 onix_init 的 CRC

UEFI 没有 VGA 文本模式。内核的 Multiboot2 头没有声明接受 framebuffer，GRUB 在跳进内核前按 `gfxpayload=auto` 切到图形模式，并打印上面的警告。

图形模式切换时，GRUB 把自己的 64 位跳板写进已经加载好的内核。入口 `onix_init()` 做镜像校验：

- 魔数 `0x20220205` 仍在
- 长度和校验和字段已被清零，说明已经进入 CRC 比较
- 比较失败后把 `"kernel crc32 check failure!!!"` 写到 `0xB8000`，然后 `hang()`

此时显示停在 GOP 图形模式，`0xB8000` 的文本缓冲不会出现在 QEMU 窗口上，所以窗口是黑的。`serial_init()` 还没执行，终端里也不再有内核日志。

CPU 停在 `hang()`（`EIP = 0x438f8`）。`EDX = 0xB803A` 是这条失败信息最后一个字符的位置。

## 空洞从哪来

链接器按 4KB 给不同属性的段各自做 LOAD。链入 `usb_storage.o` 时：

| 段 | 地址 |
| --- | --- |
| `.text` | `0x20000`，大小 `0x25900`，结束于 `0x45900` |
| `.rodata` | `0x46000` |
| 中间空洞 | `0x45900`–`0x46000`，`0x700` 字节，不属于任何 LOAD |

`usb_storage.o` 的 `.text` 只有 `0x553` 字节。加上它之后，`.text` 从 `0x453B0` 顶到 `0x45900`，正好顶出这段空洞。

`objcopy -O binary` 生成的扁平镜像按虚拟地址铺开，空洞被填成 0。`generate.py` 从文件偏移 `0x8000`（对应内存 `0x20000`）一直校验到镜像末尾，这些 0 也算在 CRC 里。

GRUB 只加载 ELF 的 LOAD 段，空洞是空闲内存。带上 `usb_storage.o` 时，64 位跳板写在 `0x45900`，落在 CRC 范围内，校验失败。

去掉 `usb_storage.o` 后，`.text` 结束于 `0x453B0`。同一段跳板改放到 `0x1F000`，在入口 `0x20000` 之下，不在 CRC 范围内，所以又能启动。这不是 `usb_storage.c` 的逻辑错误，而是 `.text` 长度刚好把空洞顶到了 GRUB 会占用的位置。下一个把 `.text` 顶到页边界附近的目标文件还会再出现。

## 用 -n 收成一段

`src/makefile` 的链接参数加上 `-n`（`--nmagic`），不再按页拆开 LOAD。同一批目标文件重新链接后变成：

| LOAD | 范围 |
| --- | --- |
| Multiboot2 头 | `0x18000`，长度 `0x18` |
| 内核本体 | `0x20000` 起的一整段 |

`.text` 仍在 `0x45900` 结束，`.rodata` 紧跟着从 `0x45900` 开始。`.data` 前面若还有对齐填充，也包在这一个 LOAD 的 `filesz` 里。GRUB 会把对应的 0 一并载入并占住，跳板不会再落进校验范围，而是继续放在 `0x1F000`。

以后增加 `.o`，只是把这一段往后撑长。`generate.py` 每次按当时的镜像重算长度和校验和。不要去掉 `-n`，也不要再加一个把某段甩到远处的 `--section-start`，否则校验范围内又会出现一段谁也不加载的空洞。

## -n 之后找不到 Multiboot2 头

加上 `-n` 后，GRUB 报：

```text
error: no multiboot header found.
error: you need to load the kernel first.
```

Multiboot2 规定头必须放在文件前 32768 字节内，并且按 8 字节对齐。GRUB 从文件头开始每 8 字节找一次魔数 `0xE85250D6`。

`-n` 把段紧凑排到文件前面，头落到偏移 `0x94`。`0x94` 除以 8 余 4，扫描会跳过它，于是认为没有加载内核。

`src/kernel/start.asm` 把这一段改成 8 字节对齐：

```asm
section .multiboot2 align=8
```

重新链接后头在文件偏移 `0x98`。魔数、架构、长度、校验和四个双字相加为 0，GRUB 可以认出它。头在文件开头，内核变长也不会把它推出前 32KB。

## 与简单引导器的关系

`src/boot/boot.asm` 和 `src/boot/loader.asm` 不解析 ELF。

`boot.asm` 只把 loader 读到 `0x1000`，核对 `0x55AA` 后跳到 `0x1008`。

`loader.asm` 把 `system.bin` 读到 `0x18000`，再跳到 `0x20000`。扁平镜像的虚拟地址没有变：

| 文件偏移 | 内存 | 内容 |
| --- | --- | --- |
| `0` | `0x18000` | Multiboot2 头 |
| `0x18`–`0x8000` | `0x18018`–`0x20000` | 0 |
| `0x8000` | `0x20000` | `_start` |

`_start` 仍然是 `push ebx`、`push eax`、`call onix_init`。`eax` 仍是 `0x20220205`，`ebx` 仍指向 ARDS。CRC 仍从镜像偏移 `0x8000` 算起，和加载后的 `0x20000` 对齐。
